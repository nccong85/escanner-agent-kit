# エージェントガイドライン

[Claude Code サブエージェントのドキュメント](https://code.claude.com/docs/en/sub-agents)と照合済みです。

## 1. エージェントはいつ必要か

最も軽いツールを使います。

- **メインセッション:** 日常の作業。
- **スキル:** ノウハウや手順。エージェントは `skills:` でスキルを事前に読み込めます。
- **エージェント:** 独立性、権限の制限、またはバックグラウンド/並列作業が必要な場合のみ。

## 2. 命名: `<scope>-<role>`

名前はエージェントが何をするかを示し、サフィックスは何をしてよいかを示します。

| サフィックス | 意味 |
|---|---|
| `-coder` | コードを書きます。レビューはしません。 |
| `-expert` | 自分の担当領域でコードを書き、レビューもします。 |
| `-reviewer` | レビューのみ。`Write` は自分のレポートファイルに対してのみ許可されます。 |
| `-checker` | 領域横断の詳細チェック (セキュリティ、パフォーマンス)。権限はレビュアーと同じです。 |
| `-tester` | テストを実行し、結果を報告します。 |
| `-researcher` | 読み取り専用の調査。 |

## 3. 基本ルール

- **ある種類の指摘を出すのは 1 つのエージェントだけにします。** 複数のエージェントが同じ diff をレビューする場合 (たとえば `flutter-reviewer`、`performance-checker`、`security-checker` を並列で実行する場合)、担当範囲が重なると次の問題が起きます。

  - 重複: 1 つの欠陥が何度も報告され、コストが倍になる。
  - 競合: 2 つのエージェントが同じ行に正反対の変更を求める。

- **frontmatter はドキュメントどおりに書きます。**

  - ドキュメント化されたフィールドのみを使います。必須なのは `name` と `description` だけです。
  - `description` には*いつ*委譲するか ("Use when …") を、短く引用符で囲んで書きます。全エージェントの description は 15,000 トークンの予算を共有します。
  - MCP: サーバー全体は `mcp__<server>__*` と書きます。素の `mcp__<server>` は `disallowedTools` でのみ機能します。
  - 色: red, blue, green, yellow, purple, orange, pink, cyan。
  - プラグインエージェントは `hooks`、`mcpServers`、`permissionMode` を無視します。
- **プロジェクト共通の事実 (テストコマンド、予算、フォルダーなど) は 1 つのファイルにだけ書きます。** 各エージェントは独自に定義せず、「まずそのファイルを読む」と記述します。

## 4. 権限

- **エージェントには必要なツールだけを付与します。**

  - `tools:` 行は必ず書きます。書かないとエージェントは*すべての*ツール (すべての MCP ツールを含む) を得ます。
  - レビュアーは読み取りとレポートの書き込みしかしないので、`Edit` は与えません。
  - ほぼすべてを許可して一部のツールだけをブロックしたい場合は、ブロックするものを `disallowedTools` に列挙します。
  - `tools:` を通じてエージェントが他のエージェントを呼び出せるようにしてはいけません。
- **重要なルールはプロンプトだけでなく、フックやスクリプトで強制します。**
- エージェントが実機での実行、ビルド、リリースを行う前には**確認を取ります**。

## 5. レビューループ

- **コーダーに即時修正させるのは Critical/High の指摘だけです。** Medium/Low はリストに載せ、機能が完成した時点でまとめて 1 回レビューします。
- **2 回目以降のレビューでは、レビュアーは直前に修正された箇所だけを見ます。** diff 全体を見直すことはしません (差分レビュー)。
- **修正ラウンドは最大 2 回です。** 2 ラウンド後もブロッカーが残る場合は、停止して人間に伝えます。3 ラウンド目は収束せず、新しい指摘を生みがちです。
- **「完了」と言うのは、テストが実際に実行されて結果が出たときだけです。** ビルドが通っただけでは不十分です。
- **エージェントは決まった形式で結果を返します** (たとえば `ACTION: REVIEW_REQUIRED` 行と変更したファイル)。これにより、メインセッションは推測せずに結果を読み取れます。

## 6. 検証

1. **テストの前に、Claude Code に新しいバージョンを読み込ませます。**
2. **エージェントに小さな確認タスクを与えます。**

   - 持っているツールを尋ね、`tools:` 行と比較する。
   - MCP ツールを 1 つ (たとえば serena) 呼び出させ、呼び出しが機能することを確認する。
   - フックがブロックすべきコマンドを実行させ、ブロックされることを確認する。
3. **正直に報告します。**

## チェックリスト

1. 独立性、権限の制限、または並列作業が必要か。不要ならメインセッションかスキルを使う。
2. 既存のエージェントと重なるか。重なるならそのエージェントを拡張する。
3. 名前は `<scope>-<role>`。
4. frontmatter: `name`、`description` (いつ使うか)、最小限の `tools`、`model`、`color`、必要なら `skills`。
5. 本文: プロジェクト事実ファイルへの参照、役割 (2〜3 行)、厳守ルール、手順、ハンドオフブロック。
6. ルーティングテーブルと、このエージェントに委譲するすべてのワークフローに登録する。
7. セクション 6 のとおりに検証する。

## テンプレート

```markdown
---
name: <scope>-<role>
description: "<What it does> in <scope>. Use when <when to call it>."
tools: Read, Grep, Glob, Bash, Write, <Edit if it writes code>, <mcp__server__* if needed>
model: <model>
color: <allowed color>
---

## Binding context
Read <shared project facts file> first. It overrides this file on conflict.

## Role
<Two or three lines.>

## Hard rules
- <Rules specific to this area.>

## Method
1. <Steps.>

## Hand-off
<The exact block the orchestrator parses.>
```
